MASTER DEVELOPMENT PROMPT
Complete Web-Based School Management System
You are a senior full-stack software architect and developer. Design and implement a production-ready single-school Web-Based School Management System for a Nigerian primary and secondary school.
The system must be secure, scalable, responsive, maintainable, role-based, and designed for real-world school operations.
Do not omit any requirement in this specification.
Do not create unnecessary functionality outside the specification unless it is required for security, reliability, maintainability, accessibility, or proper implementation of an existing requirement.

29. CBT EXAM SECURITY / EXAM MODE
When a student starts a CBT examination, enter a dedicated Exam Mode.
The student should not intentionally leave the examination environment.
Detect where technically possible:
Browser tab switching
Visibility change
Browser/window losing focus
Navigation away from exam
Minimize/leave exam window
Reload/attempted navigation
Application switching where the browser/device can detect it
A normal web application cannot guarantee complete operating-system-level application lockdown.
Therefore implement browser-level detection and locking.
For genuinely strict computer-lab lockdown, support deployment in a managed kiosk/browser environment.

30. EXAM LOCK

103. CRITICAL BUSINESS RULES
These rules must never be accidentally removed during development.
Rule 1
Teachers only access students in classes assigned to them.
Rule 2
Teachers only manage academic resources within their assigned class/subject scope.
This applies to:
CBT questions
CBT exams
Assignments
Notes
Results
Rule 3
Admins can access all school students and staff.
Rule 4
Admins can reassign staff roles and classes.
Rule 5
Super Admin and School Admin have unrestricted school-wide access, except that Super Admin has additional system-only functions.
Rule 6
Only Super Admin can access ID-card management.
Rule 7
Only Super Admin can generate/assign scratch-card tokens.
Rule 8
ID-card and scratch-card functionality must not even appear in other users’ navigation.
Rule 9
Frontend hiding is not security. Backend/RLS authorization is mandatory.
Rule 10
CBT scores are automatically recorded from the CBT engine.
Rule 11
Teachers should not manually re-enter automatically generated CBT scores.
Rule 12
CBT must save progress locally.
Rule 13
Network loss must not unnecessarily destroy CBT progress.
Rule 14
Pending examination uploads must remain available until successfully synchronized.
Rule 15
Students must see their CBT score after submission before leaving the result screen.
Rule 16
Less than five minutes remaining must produce a red/blinking timer warning.
Rule 17
When time reaches zero, the exam automatically submits.
Rule 18
Leaving the detectable examination environment locks the examination.
Rule 19
Only authorized staff can unlock a locked exam using a server-validated exam code.
Rule 20
Every result-checking scratch card has five attempts per term.
Rule 21
Scratch-card attempt deduction must be server-side/database-side and atomic.
Rule 22
Mid-term results must remain available for end-of-term result calculation.
Rule 23
Result weighting must be configurable.
Rule 24
Super Admin interactions must not enter the normal school audit log.
Rule 25
Local result uploads must be validated and protected against duplicate submissions.

105. IMPLEMENTATION PRINCIPLE
Do not treat this as a collection of disconnected pages.
Build it as one integrated school-management platform where:
AUTHENTICATION      +ROLES      +PERMISSIONS      +ACADEMIC STRUCTURE      +STUDENT DATA      +TEACHER ASSIGNMENTS      +CBT      +RESULTS      +ATTENDANCE      +ASSIGNMENTS      +NOTES      +PAYMENTS      +NOTIFICATIONS      +ANALYTICS      +E-RESULT      +SCRATCH CARDS      +ID CARDS      +AUDIT
all share the same underlying data model and authorization system.
Prioritize data integrity, security, role isolation, offline reliability, and maintainability over simply producing a visually complete interface.
Before implementing complex database tables, validate relationships and workflows so that the final schema correctly supports all requirements above.
Do not hard-code school-specific grading percentages until the school provides them.
Do not give teachers access to information outside their assigned class/subject scope.
Do not expose Super Admin-only functionality to other roles.
Do not rely on frontend restrictions for authorization.
The finished system must be production-oriented and suitable for actual deployment to a Nigerian primary/secondary school using Next.js, Supabase, Resend, and Vercel.
